权限判定流水线

工具执行前的一道五层闸门。前两层只能拒绝、不能放行， 规则层可以放行，档位兜底把没人表态的情况变成放行或提问， 最后由人在回路消解提问。判定层不引用任何界面模块。

01

五层的顺序与权力

顺序本身就是设计的全部要点：每一层能给出的表态不同， abstain（不表态）意味着交给下一层，而不是通过。

02

三条不变量

这三条约束写在类型定义的注释里，是整套设计的承重墙。破坏任何一条，流水线的安全性就不再成立。

  • I

    前两层没有放行能力，通过它们不等于获得放行。

    黑名单与沙箱的返回类型只允许 deny 与 abstain， 因此不可能成为跳过后续层的通道。 permission/types.ts:30-34（spec F2、N2）

  • II

    四档中没有任何一档的兜底是直接拒绝。

    MODE_FALLBACK 的值域只有 allow 与 ask。 档位只决定「默认放行还是默认问一句」，不承担拒绝职责。 permission/limits.ts:58-68（spec F14）

  • III

    命中的规则不受档位影响。

    兜底只在规则未命中时生效。写进配置的 allow / deny 是显式意图， 切档不会改写它。（spec F15）

03

调用链

界面负责组装 PermissionGate 并原样透传，中间层不解释权限语义； 真正的判定点只有一处。

  1. tui/app.tsx:92loadPermissionConfig()

    启动时读三层 YAML，结果存进 permissionConfigRef

  2. tui/app.tsx:151buildGate() → PermissionGate

    档位用 getter 读 ref，规则集直接引用 ref

  3. tui/app.tsx:258runLoop({ permission: gate })

    每轮重建 Gate，注入 ReAct 循环

  4. agent/loop.ts:142runBatches(batches, registry, { workDir, signal, permission })

    循环只做透传，自己不读 Gate 里的任何字段

  5. agent/batch.ts:54runTool(registry, call.name, call.arguments, context)

    ToolContext 是 Gate 的载体

  6. tools/execute.ts:40decide(tool, validation.value, context)

    判定点。拒绝时返回 fail("permission_denied", reason)

  7. tools/execute.ts:47tool.execute(validation.value, context)

    仅在放行后执行；拒绝路径下一次都不会被调用

判定用归一化后的参数

传给 decide 的是 validation.value 而非原始 args， 也就是 schema 校验之后的值。规则匹配与沙箱取值因此看到的是同一份数据， 不会出现「校验前后不一致导致判定被绕过」。

拒绝是零副作用的

判定在执行之前，拒绝时直接返回工具结果， permission_denied 在 ToolErrorKind 里单列， 模型能把它和越界、参数错误区分开。

04

逐层逻辑

第一层 · 危险命令黑名单

只对 Bash 生效，其他工具直接不表态。可变空白统一写成 \s+， rm  -rf  / 这类多空格写法绕不过去。 拒绝文案明确写了「该限制不可通过配置或权限档位放开」。

第二层 · 路径沙箱

分两路取路径，最后汇到同一个解析函数。

  • PATH_ARG_BY_TOOL文件类工具按字段名取：Read / Write / Edit 取 file_path，Glob / Grep 取 path
  • extractPathCandidates()Bash 先剥出引号内容，再按 && || ; | 与空白切词，挑出「看着像路径」的 token 并去重
  • resolveInside()两路共用。realpath 到最近的已存在祖先再拼回缺失段，所以绝对路径、.. 上跳、符号链接逃逸都拦得住，同时能处理「目标文件尚未创建」的写入场景

与工具内部的重复是有意的

各工具的 execute 内部也会调 resolveInside。 沙箱层保留这份重复，是为了让它作为一道不可放开的独立层存在—— 即使某个工具将来忘了自查，闸门仍在。（sandbox.ts:44，plan P4）

第三层 · 规则匹配

规则文本形如 Bash(git *)：取首个 ( 与末个 )， 允许模式内含括号，但 ) 必须落在末尾。

  • 层间优先级session > local > project > user，高优先层命中即定，不再往下看
  • 层内优先级同层多条命中时取 order 最大的，也就是书写靠后的赢
  • 匹配主体Bash 用 command 原文；文件类工具用 toPosix() 归一化后的路径
  • 通配语义pattern 不含 * 时做精确整串比较；含 * 时转成 [\s\S]*，不区分 * 与 **

第四层 · 档位兜底

由 MODE_FALLBACK × classifyTool() 查表。 分类规则很简单：readOnly 归 read，Bash 单列，其余算 write。

第五层 · 人在回路

gate.confirm 返回一个挂起的 Promise，由 ConfirmBox 的按键兑付。 确认框与输入框互斥挂载，避免两个 useInput 争抢同一批按键。

  • once 本次放行只对这一次调用生效，不落任何存储
  • session 本会话放行规则 push 进内存 session 层，跨轮存活、进程退出即失效
  • always 永久放行追加到 .mewcode/config.local.yaml 末尾，同时 push 内存 local 层，本进程立即生效不重读文件
  • deny 拒绝返回 permission_denied，原因为「用户拒绝了此操作」

永久放行写的是精确整串

ruleTextFor() 直接用当次调用的命令原文或路径，不做任何泛化。 确认框在选中「永久放行」时会把即将写入的规则文本显示出来—— 授权范围要在点头前看清，避免一次确认授出比预期更大的权限。

05

配置与运行期状态

loadPermissionConfig() · permission/config.ts:23-42 · 按此顺序读取

三层文件分别读取，刻意不复用 mergeConfig——合并会丢掉来源分层， 而分层就是优先级本身。permission_mode 字段后读覆盖先读； 非法值退回默认档并记一条告警。

解析失败不静默放开

YAML 解析异常、顶层不是对象、permissions 不是列表、 单条规则解析不出来——都只产生 warning 而不影响其他规则， 启动时在对话区以 system 消息呈现一次。

写盘位置决定优先级

appendLocalRule() 追加到 permissions 数组末尾， 即本层顺序最后、层内优先级最高。目录不存在时递归创建。

为什么状态全走 ref

运行期状态用 useRef 而非 useState，两处都是为了避免闭包捕获旧值。

  • rulesRef会话级放行要跨轮累积；Gate 每轮重建时必须读到最新规则集
  • permissionModeRef配合 buildGate() 里的 get mode()：本轮跑到一半按 Shift+Tab，剩余调用也按新档判定。用 state 快照会让整轮都停在旧档

切档只有一个入口 switchPermissionMode()，同写 state 与 ref。 它是纯模式开关：不写会话历史、不发模型请求。 触发方式有两种——Shift+Tab 循环切档（确认框弹出时不切）， 以及斜杠命令 /plan /do /accept-edits /bypass。

06

两个方向的防死锁

「挂起等待人回答」这件事有两种死法：没人能回答，或者有人问了但没人兑付。两边都堵上了。

没人能回答 → 拒绝，不挂起

  • gate 缺省非 TUI 入口与测试环境。按 default 档查表，需要确认的一律拒绝
  • gate.confirm 缺省同样直接拒绝，理由为「当前环境无法交互确认」
  • confirm 抛错catch 后走同一条拒绝路径

问了没人兑付 → 先按拒绝结清

Esc 中断时，如果有挂起的确认，先 settleConfirm("deny") 再 abort。 否则 Promise 永久悬空，runLoop 收不了尾，整个会话卡死。

tui/app.tsx:180-184

同一时刻最多一个确认框

这不是靠加锁保证的，而是两个事实的乘积：只读工具在四档里都是 allow， 永远走不到 ask；而写类工具与 Bash 各自单独成串行批。 所以 confirm 只可能在串行批里被调用，并发批里不会出现。

07

三点值得留意

三条性质不同：一条要你确认设计意图，一条是明确的错误路径缺陷，一条是既有取舍的另一半。

  • 计划模式并不阻止改文件

    设计取向 · 待确认

    MODE_FALLBACK 里 plan 与 default 的取值逐格相同。 agent/loop.ts:110 的注释说明这是有意的：计划模式不再靠摘掉工具， 改由权限层逐次确认承担。

    代价是计划模式只是「每次问一次」，而 ConfirmBox 的默认光标停在第一项 本次放行。习惯性按 Enter 就会在计划模式下改文件。

    如果计划模式的定位是「只看不改」： 把 write 的兜底改成 deny，或让默认光标落在「拒绝」上。 前者改语义，后者只改默认值——取决于你要的是硬约束还是软提醒。

  • 永久放行写盘失败会被报成流错误

    缺陷 · 改动很小

    appendLocalRule 抛错时没有被捕获，异常一路冒到 runLoop 的 总 catch，最终以 stream_error 收尾。用户看到的提示是 「本轮因请求错误中止」，而实际原因是配置文件写不进去。

    decide.ts:63-75（无 try） → execute.ts:40（在 try 之外） → batch.ts:106 rethrow → loop.ts:156-158 catch → finish("stream_error")

    建议：在 grantAlways 调用处包一层 try， 失败时退化成本会话放行并给出真实提示。本次调用已经获得用户点头， 不该因为持久化失败而连带中止整轮。

  • Bash 路径识别是纯文本判断，有漏网方向

    既有取舍 · 文档不完整

    looksLikePath() 只认三种形态：以 / 开头、 X:\ 盘符、含 .. 段。 像 cat $HOME/.ssh/id_rsa 三条都不满足，沙箱不表态—— 这类命令的实际兜底是黑名单加档位 ask，而不是沙箱。

    源码注释已标注了反方向的误判（grep -r ".." . 里的 .. 会被当成路径）， 漏网方向没写，属于同一取舍的另一半。

    建议：要真正收紧得引入 shell 词法解析，成本不小。 低成本的一步是把「不带 / 前缀但含 /」的 token 也纳入候选， 并把漏网方向补进注释。
