# System Prompt Spec

## 背景

前三章已经建好对话闭环、工具层与自主循环。但全局指令始终停留在占位阶段：每个模块只有
一行内容（身份「你是 MewCode」、系统约束「优先给出准确回答」之类），模型拿到的行为约束
几乎为零。表现出来的问题是：该用专用工具的地方用命令行拼凑、改文件不先读原文导致替换
失败、输出啰嗦或答非所问。

缓存方面的实际状态与直觉相反，实测后修正如下（按 CJK 字符 1 token、其余 4 字符 1 token
估算，误差约 ±15%）：

| 前缀分段 | ~tokens |
|---|---|
| 工具定义（执行模式，6 个） | 829 |
| 系统提示词稳定部分（当前占位内容） | 473 |
| 环境信息 | 67 |
| 合计（当前单一缓存单元覆盖范围） | ~1369 |

可缓存长度门槛按整个请求前缀计算，工具定义也计入其中。当前前缀已超过门槛，因此缓存
标记是有效的、能够命中。真正的问题在于：系统提示词整体作为单一缓存单元，其中混入了
每天变化的日期与切分支即变的 Git 分支，任一变动就让整段前缀连同工具定义一起作废。也就是
说缓存每天至少重建一次，开发期频繁切分支时更多。本章在这一项上做的是止损，不是修复
失效功能。

另有一处需要在实现时验证的边界：计划模式只暴露只读工具，工具定义降至约 426 token，
加上当前稳定内容 473 token 合计约 899 token，低于门槛。稳定内容展开后应自然越过门槛，
但这是硬性条件而非推论。

此外还缺一条运行期注入通道：会话级开关（如计划模式）的指令目前直接拼进系统提示词，
切一次模式就污染整个缓存前缀；而已有的「系统提醒」写入方式在 Anthropic 协议下会被静默
丢弃，三种协议行为不一致。

本章把全局指令展开成结构化、可扩展的模块化系统提示词，把稳定内容与变化内容分到两个
缓存单元，并新增一条运行期补充指令注入通道，让 MewCode 从「能干活」变成「干得好」。

## 关键决策

以下四条在需求澄清中已与用户确认，记录选择与理由：

- D1: 环境信息保留在系统提示词内、位于全部模块之后，但单独构成第二个缓存单元。
  仅调整位置不解决问题——只要与稳定内容共用一个缓存单元，日期或分支一变，前面所有
  内容一起失效。分成两个单元后，跨天与切分支只影响环境信息这一小段。
- D2: 切换会话模式时接受一次缓存重建，不为缓存而放弃工具集过滤。
  可缓存前缀顺序为「工具定义 → 系统提示词 → 消息」，模式切换会改变暴露的工具集，
  排在其后的内容必然无法命中。模式切换是低频操作，代价可接受；放弃工具过滤会削弱
  计划模式的实际约束力，且与上一章的验收标准冲突。
- D3: 运行期注入的补充指令不写入会话历史，只在构造请求时挂到当次消息上。
  若写入历史，历轮注入的旧指令会永久堆积并持续占用上下文，且其中绝大多数已过期；
  只在发送时挂载则每轮只带当轮所需的一份。
- D4: 本章范围只覆盖系统提示词侧的缓存分层，不含消息通道的缓存断点。
  会话历史末尾的断点标记当前对纯文本用户消息与工具结果消息两种形态都不生效，属于
  已知缺陷，但按用户决定推迟到后续章节处理。

## 目标

- 把全局指令按职责拆成互不重叠的模块，按优先级组装成完整系统提示词，新增模块只需
  声明优先级而不必改动组装逻辑。
- 把每个模块从一行占位内容展开为真正可约束模型行为的结构化指令。
- 区分稳定内容与变化内容：工具定义与稳定指令构成第一个缓存单元，环境信息构成第二个，
  对话历史与运行期指令走消息通道。
- 在工具描述与全局指令两处重申同一批关键约定，提高模型对「优先用专用工具」「编辑前
  必先读」这类规则的遵守率。
- 提供一条运行期补充指令注入通道：既不污染缓存前缀，也不会被模型当成用户输入来回复，
  且不随轮次在历史中累积。
- 会话级开关的指令按轮次控制注入强度：首轮完整、间隔固定轮数重复完整、其余轮次精简。
- 通过解析接口返回的缓存用量字段验证策略是否真的生效，并准备一组典型场景做人工对比
  作为定性评估。

## 功能需求

### 一、系统提示词模块化

- F1: 模块化组装
  系统提示词由若干模块组装而成。每个模块声明自己的名称、优先级与内容，组装时按优先级
  从前往后排列，模块之间以一个空行分隔。组装逻辑只依赖优先级，不内置模块名清单；新增
  一个模块只需声明其优先级并加入组装序列。

- F2: 七个固定模块
  固定模块按优先级依次为：身份、安全边界、任务模式、行为、代码规范、工具使用、输出风格。
  每个模块的内容从一行占位扩展为结构化指令段，各自职责为：
  身份说明助手是谁、工作在什么环境；安全边界给出不可违反的硬性约束（工作目录范围、
  密钥不回显、不擅自执行破坏性操作）；任务模式说明存在计划与执行两种模式及各自含义；
  行为规定动手前先读、改动范围最小化、不可逆操作先确认；代码规范给出写代码时遵循的
  约定；工具使用给出可用工具清单与调用约定；输出风格规定中文作答、表达基调与终端呈现
  约定（路径与代码的写法、篇幅与结构的取舍）。

- F3: 模块职责互斥
  同一条约束只在一个模块中出现，不同模块的内容不重复、不互相矛盾。（跨通道的规则重申
  见 F17–F19，与本条不冲突：本条约束的是系统提示词内部。）

- F4: 三个可选模块
  自定义指令、已激活的 Skill、长期记忆作为可选模块排在固定模块之后、环境信息之前。任一
  可选模块内容为空或仅含空白字符时不进入组装，不产生空标题或多余空行。本章只提供注入
  位置与组装行为，不实现内容来源。

- F5: 环境信息模块
  环境信息作为系统提示词的最后一段，包含：工作目录、操作系统与架构、Shell、是否为 Git
  仓库及当前分支、当前模型标识、当前日期。取不到某项时（如非 Git 仓库）给出明确取值，
  不留空、不中断启动。

### 二、缓存分层

- F6: 两个缓存单元
  系统提示词以两段发出并各自标记缓存断点：第一段含全部固定模块与可选模块，第二段含
  环境信息。第一个断点覆盖「工具定义 + 第一段」，第二个断点覆盖「工具定义 + 第一段 +
  第二段」。环境信息的变动（跨天、切分支）不导致第一个缓存单元失效。

- F7: 稳定段逐字节稳定
  同一会话、同一模式下，第一段在任意轮次重复构造的结果逐字节一致：不含时间戳、随机值、
  轮次计数、已用 token 数等随轮次变化的内容。

- F8: 工具定义可缓存
  工具定义随请求一同进入可缓存前缀，且同一模式下重复请求时其序列化结果顺序与内容逐
  字节一致，不因遍历顺序或对象键序抖动。

- F9: 模式切换不重建稳定段
  切换会话模式不改变第一段的内容，也不需要重建客户端。模式带来的差异只体现在暴露的
  工具集与运行期注入的指令上。（工具集变化仍会导致该次请求整体前缀重建，见 D2。）

### 三、运行期指令注入

- F10: 补充指令的消息形态
  运行期注入的补充指令以约定标签包裹，作为消息通道的一部分随请求发出。该形态需让模型
  将其识别为系统级背景说明而非用户提问，不对其内容本身作答。标签的具体写法由技术设计
  阶段确定。

- F11: 注入不污染缓存前缀
  补充指令进入消息通道，不进入系统提示词的任一缓存单元，其内容变化不导致两个缓存单元
  失效，也不改变断点位置。

- F12: 注入内容不累积
  补充指令不写入会话历史，只在构造当次请求时挂载。连续多轮对话后，历轮的旧补充指令
  不残留在上下文中；同一轮内不重复挂载同一条指令。

- F13: 三种协议行为一致
  补充指令在三种协议（Anthropic、OpenAI Responses、OpenAI 兼容）下都必须真正到达模型。
  当前实现中系统角色消息在 Anthropic 协议下被静默丢弃，新通道不得沿用这一形态。

### 四、模式指令按轮次注入

- F14: 模式状态与注入强度
  会话维护当前模式（计划 / 执行，默认执行）。计划模式下每轮通过 F10 的通道注入模式指令，
  注入强度按该模式下已进行的轮次决定：首轮注入完整版（说明只能读取信息、应当产出计划
  而非直接改动、切回执行模式后才动手）；此后每隔 5 轮再次注入完整版；其余轮次注入精简版
  （一句话提示当前处于计划模式）。间隔轮数在实现层单点声明。

- F15: 模式切换重置计数
  切换模式时重置轮次计数，使新模式的第一轮拿到完整版指令。执行模式不注入模式指令。

- F16: 稳定段不含当前模式
  第一段的任务模式模块只描述两种模式的机制与含义，不声明当前处于哪个模式；当前激活的
  模式只通过运行期注入通道传达。工具使用模块中不再内嵌计划模式的行为约束。

### 五、关键规则双重强化

- F17: 工具描述内嵌关键约束
  在工具自身的描述中直接写明与该工具相关的关键约定，至少覆盖：编辑或写入文件前必须
  先读取当前内容；查找文件与搜索内容优先使用专用工具而不是用命令行拼凑；文件路径使用
  相对于工作目录的相对路径。

- F18: 全局指令重申同一批规则
  系统提示词的工具使用与行为模块重申 F17 中的同一批规则，形成跨通道的双重强化。

- F19: 两处措辞不冲突
  工具描述与全局指令对同一条规则的表述必须一致，不出现一处要求、另一处放宽的情况。

### 六、缓存效果可观测

- F20: 缓存字段解析
  解析接口返回的缓存相关用量字段，至少区分「缓存读取命中」与「缓存写入创建」两类，并在
  一轮内多次模型请求时累计。Anthropic 与 OpenAI 系协议各自可取到的字段不同，取不到的项
  以零值呈现而不是报错。

- F21: 缓存命中可见
  当前轮的缓存读取与缓存创建 token 数在界面状态栏上分别可见，两个数分开呈现而不是合成
  单一数值或百分比，用户不必查看日志即可判断缓存处于命中还是重建状态。

- F22: 定性评估场景集
  提供一组固定的典型场景描述（至少覆盖：只读探查类请求、单文件修改类请求、需要多轮
  迭代的任务、计划模式下的方案输出），用于在提示词调整前后做人工对比。本章只交付场景
  描述与观察维度，不做自动化评分。

## 非功能需求

- N1: 达到最小可缓存长度
  两个缓存单元各自覆盖的前缀长度均需超过所使用模型的最小可缓存前缀长度门槛，否则缓存
  标记不生效。需覆盖计划模式这一最短情形（只读工具集 + 稳定段）。门槛值与判断方式需在
  实现层记录，便于后续更换模型时复核。

- N2: 缓存命中有效
  同一会话连续多轮对话中，除首轮与模式切换后的首轮外，后续请求应观察到第一个缓存单元
  命中（缓存读取 token 数大于零）。跨天或切换分支不影响这一结论。

- N3: 提示词长度受控
  结构化不等于堆砌：完整系统提示词的总长需控制在一个明确的量级内，模块内容以约束行为
  为准，不写与行为无关的说明性文字。

- N4: 向后兼容
  未配置工具、无任何可选模块、非 Git 目录等情况下系统提示词仍可正常构造并发出请求。
  配置文件格式保持兼容，不新增必填字段。纯文本对话的交互与呈现不变。

- N5: 模块可扩展
  新增一个模块只需声明名称、优先级与内容，不改动组装逻辑、缓存分段逻辑与调用方代码。

- N6: 注入频率可控
  运行期注入不得每轮全量重复：完整版指令的注入间隔集中单点声明，可调整而不改动注入
  逻辑。

- N7: 密钥不进提示词
  环境信息不含任何密钥、令牌或凭据值。可选模块的内容来源在后续章节接入时同样受此约束。
  提示词构造过程中不读取环境变量中的密钥类字段。

- N8: 上限集中声明
  模块优先级、完整版指令的注入间隔轮数与缓存长度门槛集中单点声明，与既有资源上限放在
  一处。

- N9: 可测试性
  提示词组装、缓存分段与注入逻辑均不依赖界面与真实网络：可直接断言模块顺序、稳定段逐
  字节一致性、可选模块为空时不产生空段、注入内容不进历史。测试通过既有测试命令运行，
  类型检查无错误。

- N10: 代码风格一致
  遵循现有约定：严格类型检查、模块按领域分层、中文行内注释、上限集中定义。不引入与现有
  依赖重复的第三方库。

## 不做的事

- 消息通道缓存断点：会话历史末尾的断点标记当前对纯文本用户消息与工具结果消息两种形态
  都不生效，本章保持原样不动，推迟到后续章节。
- 项目指令文件加载：不扫描、不读取、不合并项目根目录下的指令文件；只留可选模块的注入
  位置。
- 自动记忆：不实现记忆的生成、存储、召回与写回；只留可选模块的注入位置。
- Skill 的发现与激活：不实现 Skill 的扫描与匹配；只留可选模块的注入位置。
- 真实 MCP 接入：不连接 MCP 服务端，工具清单仍来自内置注册表。
- 自动化评估：不做打分脚本、不做回归基线、不做提示词 A/B 的自动统计；只交付人工对比用
  的场景描述。
- 上下文压缩与历史裁剪。
- 提示词的运行时热更新、按项目切换模板、用户自定义模块顺序。
- 缓存费用的换算与展示：只呈现 token 数，不折算金额。
- 提示词内容的多语言版本：只提供中文。

## 验收标准

### 系统提示词模块化

- AC1: (F1) 组装结果中各段按声明的优先级顺序出现，段落之间以一个空行分隔；临时新增一个
  优先级居中的模块，它出现在预期位置且无需改动组装逻辑。
- AC2: (F2) 完整系统提示词中七个固定模块均存在且内容不再是单行占位；每个模块的内容可
  对应到 F2 描述的职责。
- AC3: (F3) 逐模块检查同一条约束未在两个模块中重复出现，且不存在互相矛盾的表述。
- AC4: (F4) 三个可选模块内容为空时组装结果中不出现对应段落与多余空行；提供内容时出现在
  固定模块之后、环境信息之前。
- AC5: (F5) 环境段包含工作目录、操作系统与架构、Shell、Git 状态与分支、模型、日期六项；
  在非 Git 目录下 Git 一项有明确取值且构造不报错。

### 缓存分层

- AC6: (F6) 系统提示词以两段发出，两段各自标记缓存断点；仅环境信息发生变化时第一段内容
  不变。
- AC7: (F7) 同一会话同一模式下连续多次构造第一段，结果字符串完全相等。
- AC8: (F8) 同一模式下连续两次构造工具定义序列，序列化结果完全相等。
- AC9: (F9) 切换模式前后第一段内容完全相等，且不触发客户端重建。

### 运行期指令注入

- AC10: (F10) 注入的补充指令以约定标签包裹出现在发往模型的消息中；在真实对话中模型不会
  针对该指令内容本身作答。
- AC11: (F11) 注入内容变化时，两段的内容与两个断点的位置均不变。
- AC12: (F12) 连续三轮注入后检查会话历史，其中不含任何补充指令内容；第二轮的请求中不
  包含第一轮注入的内容。
- AC13: (F13) 同一条补充指令在三种协议下构造出的请求中都能找到其内容，无任一协议将其
  丢弃。

### 模式指令按轮次注入

- AC14: (F14) 计划模式第 1 轮与第 6 轮注入完整版，第 2 至第 5 轮注入精简版；把间隔轮数
  改为其他值时该规律随之变化。
- AC15: (F15) 从执行模式切入计划模式后的第一轮为完整版；执行模式下不注入模式指令。
- AC16: (F16) 第一段中不含「当前处于计划模式」这类声明；工具使用模块中不含计划模式的行为
  约束。

### 双重强化
