# 如何手写一个 spec 驱动开发的 skill

这份文档是给人看的，不是给 agent 读的流程。它记录 `SKILL.md` 为什么这样写，
以及你以后自己写别的 skill 时该怎么下手。

---

## 核心：这个 skill 不是教 agent 什么是 SDD

agent 已经知道什么是需求文档、设计文档。把 SDD 的定义写一遍进去，一行代码
都不会变。

skill 真正要解决的问题是：**你说"加个功能"，它三秒后就开始写代码了。** 中间
那些该想清楚的事被跳过了，不是因为它不懂，是因为没有东西拦住它。

所以这个 skill 的本质是一组**停止点**，加上每个停止点上"交出什么才算能往下走"
的定义。想清楚这一点，写出来的内容会完全不同——大部分篇幅应该是门禁、交接
契约、自检判据，而不是解释什么是 spec。

判断一句话该不该写进 skill，用这个尺子：**这句话删掉，agent 的行为会变吗？**

```
"规格驱动开发是一种先写规格再写代码的方法论"   → 删掉，行为不变。删。
"写完 spec.md 停下，等用户确认后才能进入设计"   → 删掉，它会直接往下跑。留。
"spec 里不出现方法名、字段名、文件路径"        → 删掉，它一定会写进去。留。
```

## 手写步骤

### 第 1 步：先写"不装这个 skill 会出什么问题"

不要打开编辑器就开始写流程。先列一张失败清单，只写你自己实际遇到过的：

```
- 我说加功能，它直接开始改代码，没问我边界在哪
- 需求里有歧义，它自己默选了一个方案，我到看代码时才发现选错了
- 让它改 A，它顺手把旁边的 B 也"优化"了，diff 里一半是我没要的
- 它说"应该没问题"就算验证过了，实际没跑
- 老测试挂了，它把测试改绿了，我永久失去了"行为变了"的信号
- 做到一半发现设计不对，它在代码里硬绕，没回来改设计
```

**这张清单就是 skill 的全部内容来源。** 每一条对应一条规则。不在清单上的东西
不要写——那是你想象中的问题，写进去只是稀释。

这一步是手写 skill 最关键的一步，也是最容易跳过的。跳过它会写出一篇教科书，
读起来很完整，但改变不了任何行为。

### 第 2 步：定阶段，一个阶段一个产出物

```
需求 → 设计 → 任务 → 实现
spec   plan   task   代码
```

四个够了。为什么要分开而不是一份大文档：分开才能在中间插门禁。一份文档写完，
错误已经全在里面了。

每个阶段必须恰好产出一个文件。产出两个的阶段说明该拆，产出零个的阶段不是阶段。

### 第 3 步：给每个交接口写契约

这是让 SDD 真正生效的地方，也是大部分人手写时漏掉的。

每个阶段的产出，是下一阶段唯一能依赖的输入。所以要明确写：**这份文档必须包含
什么，下一阶段才能只看它就开工。**

```
spec → plan 的契约：
  plan 阶段只能看 spec.md 和现有代码。
  所以 spec 必须写完范围边界和待定项的决议——否则设计阶段会替你猜。

plan → task 的契约：
  task 阶段只能看 plan.md。
  所以 plan 必须写出「不改动」清单——否则任务会蔓延到相邻模块。

task → 实现的契约：
  实现时只看当前那一条任务。
  所以每条任务必须自带：改哪个文件的函数、用什么命令验证、不许碰什么。
```

反过来推是个好方法：想上一步漏了什么会导致这一步出错，那个东西就是契约里
必须有的。

### 第 4 步：把门禁写成独立的一行

```markdown
**写完停下，让用户审查 spec.md，特别是待定项。**
```

三个要点：

- **每个阶段末尾都要有一句**，不能只在开头总述"每阶段要停"。开头那句在跑到
  第三阶段时会被忽略。
- **独立成行**，不要塞在段落中间。
- **给理由**，一次就够：需求写错改一段文字要几分钟，代码写错改一片文件要半天，
  门禁的收益全在这个差价里。

这几行是整个 skill 的承重墙。删掉它们，剩下的模板全变成装饰。

### 第 5 步：写死分层边界

最常坏的地方。spec 里出现 `PermissionGate.check()` 就等于设计已经做完了，
阶段 2 的门禁自动失效——你在审设计时，实现方案早就定死在需求文档里了。

所以要给每层写一条可判定的尺子：

```
spec 层：不出现方法名、类名、字段名、文件路径。
        自检——同一份 spec 能同时指导 Go / Java / TypeScript 三种实现。

plan 层：只列签名和字段，不列实现。
        自检——伪代码超过 20 行就是在写实现，退回去。

task 层：不贴真代码。
        自检——读过 plan 的人删掉某段仍能写出等价代码，那段就该删。
```

注意每条后面都跟了自检句。"spec 要写得抽象"没法执行，"能同时指导三种语言
实现"可以当尺子量。

### 第 6 步：把"怎么写"塞进模板注释，不要写在 SKILL.md 里

SKILL.md 只写流程和门禁。文档长什么样、每一节的判据、常见错误，全放到
`templates/` 里，用 HTML 注释写在对应小节旁边：

```markdown
## 验收标准

<!--
格式：<旁人可执行的操作> → <可观测结果>
反例："界面保持流畅"——没有观察方法，验收时只能靠感觉
正例："流式输出期间滚动历史区，spinner 秒数继续递增"
-->

- AC1:
```

三个好处：填文档时指导就在眼前；注释不进最终产出；哪节容易写错就在那节旁边
加约束，比集中写在别处有效得多。

**反例比正例有用。** agent 知道该做什么，但不一定知道哪个写法看着对、其实错。

### 第 7 步：只用真实措辞测触发

别用"帮我写个 spec"测，那必然触发。要用你平时真的会说的话：

```
"给 MewCode 加个工具确认，写文件前问一下用户"
"重构一下对话历史那块，现在太乱了"
```

不触发就回去改 description。description 里要枚举你实际会用的措辞，还要加一句
兜底：*"即使用户没有明确说写 spec，只要是需要动多个文件的功能开发，都应该走
这个流程。"* agent 有欠触发的倾向，抽象定义几乎不会命中。

### 第 8 步：跑一个真实功能，然后砍

第一版必然有多余的东西。跑完一个完整功能后看两件事：

- **哪一节你从来不填** → 删掉
- **哪一节你每次都要额外口头解释一遍** → 把那句解释补进注释

这一步比前七步加起来更能提升质量。skill 是磨出来的，不是想出来的。

## 三层加载机制

这是写 skill 唯一需要理解的技术细节，它决定内容放哪：

```
第 1 层  name + description        永远在上下文里
第 2 层  SKILL.md 正文             skill 触发后
第 3 层  templates/ references/    正文里指路才读
```

三条推论：

- **所有"什么时候用我"的信息只能写在 description 里。** 写在正文里等于没写，
  因为正文只有触发后才可见。这是最容易犯的错。
- **正文控制在 500 行内。** 超了就往第 3 层拆，正文只留流程骨架和指路。
- **产出物的具体格式放第 3 层。** 在正文里描述"spec 应该包含背景、目标、
  需求……"是浪费上下文，直接给一份模板文件让它读。

本目录的 `HOWTO.md`（就是这份文件）属于第 3 层，不会自动进上下文。

## 硬规则（违反了 skill 直接不工作）

| 项 | 要求 |
|---|---|
| 文件名 | 必须是 `SKILL.md`，全大写 |
| 目录名 | kebab-case，且与 frontmatter 的 `name` 完全一致 |
| frontmatter | 文件开头三横线包裹的 YAML，`name` 和 `description` 必需 |
| description | 写成一行。YAML 里换行需要额外语法，写错会导致整个 frontmatter 解析失败 |
| 引用路径 | 相对 SKILL.md 所在目录，如 `templates/spec.md` |

目录名和 `name` 不一致是最常见的坑，两个写成一样就不用赌。

## 从多小开始

不要一上来写四个模板。手写的正确起点是**只有门禁、没有模板**的三十来行：

```markdown
---
name: spec-flow
description: 规格驱动开发工作流。当用户提出新增功能、重构模块，或提到 "spec""规格""需求文档" 时使用。即使用户没有明确说写 spec，只要是需要动多个文件的功能开发，都应该走这个流程。
---

# 规格驱动开发

需求写错时改一段文字要几分钟，代码写错时改一片文件要半天。下面的门禁，
收益全在这个差价里。

文档放 `specs/<功能名>/`。

## 1. 需求 → spec.md

写：背景、目标、功能需求、失败模式（每个功能问一句"这步失败会怎样"）、
不做的事、验收标准（每条是「旁人可执行的操作 → 可观测结果」）。

歧义单独列一节，写清"我暂时按 X 处理，理由 Y"。不要默选方案闷头往下走。

不出现方法名、类名、文件路径。自检：这份 spec 能同时指导 Go / Java /
TypeScript 三种实现吗？

**写完停下，等用户确认，特别是歧义那一节。**

## 2. 设计 → plan.md

先读现有代码。写：改动范围表（含「不改动」清单）、数据结构与接口签名、
调用链、关键决策及理由。

spec 的每条需求都要在设计里有落点。找不到落点的，在文档里标出缺口，
不要用代码硬绕。

**写完停下，等用户确认。**

## 3. 任务 → task.md

每条任务三件套，缺一不可：
- 锚点：具体文件路径 + 函数名。缺了我会自己找地方改。
- 验证：可粘贴的命令 + 预期输出。缺了"应该没问题"会被当成结论。
- 禁止：具体文件名或函数名。缺了我会顺手重构邻近模块。

第一条任务做纯机械、不改行为的变更，先拿到一次干净的绿色验证作基线。
粒度 2-5 分钟，超过就拆。

预期会失败的地方写明"这是预期的，只报告失败清单，不要改测试"。不写，
我会把测试改绿，你就永久失去了"行为确实变了"的信号。

**写完停下，等用户确认。**

## 4. 实现

一次一条任务：只写这条需要的代码 → 跑验证命令 → 贴真实输出（不是预期
输出）→ 勾掉 checkbox → 停下等确认。

## 规则

- 用户说"直接写代码"时，提醒至少需要 spec.md。
- 需求变更先改 spec.md 再往下同步。代码和 spec 漂移后，spec 变成误导性
  文档，比没有更糟。
- 实现时发现设计不对，停下说明问题，回第 2 步改设计。
- specs/ 进 git。它是 code review 的输入，先读 spec 再看 diff。
```

这三十行已经能干活了。跑两三个功能，发现每次都要重复解释某个文档该怎么写，
才把那部分抽成 `templates/spec.md`。模板是从重复劳动里长出来的，不是提前
设计出来的。

## 一次真实会话长什么样

```
你：给 MewCode 加个危险工具二次确认，写文件和跑 shell 命令前要先问用户

它：[spec-flow 触发]
    → 读 templates/spec.md，产出 specs/tool-confirm/spec.md
    → 停下，列出待定项：
      Q1：参数很长时（比如写入 500 行文件）展示要不要截断？暂取截断 20 行
      Q2：非交互环境（CI、管道输入）下危险工具是拒绝还是放行？暂取拒绝

你：Q1 按你说的，Q2 拒绝并返回明确错误，不要挂起等待

它：→ 更新 spec.md
    → 读现有代码，读 templates/plan.md，产出 plan.md
    → 停下

你：拦截层的位置同意，但会话放行不要落盘，进程退出就失效

它：→ 改 plan.md 的关键决策表
    → 产出 task.md（T1 加空壳拦截层 → T2 判定逻辑 → T3 交互分支 → T4 接入主循环）
    → 产出 checklist.md
    → 停下

你：T1 开始

它：→ 只做 T1，跑验证命令，贴真实输出，停下

你：继续 T2
```

四个门禁一个都不能省。一口气跑完四步，等于换个姿势 vibe coding。

## 三个最容易犯的错

**写成教科书。** 大段解释 SDD 的价值和方法论。判据还是那句：删掉这段，agent
的行为会变吗？

**门禁只在开头写一次。** "本流程每阶段结束需确认"放在开头，然后四个阶段各自
往下写。跑到第三阶段那句话已经不起作用了。必须每个阶段末尾各写一行。

**用 MUST 代替理由。** `必须先写 spec.md` 不如 `需求写错改一段文字，代码写错
改一片文件`。给了理由，agent 遇到规则没覆盖的情况能自己判断；只给禁令，遇到
意外就乱来。大写的 ALWAYS / NEVER 出现时，基本都是该换成一句解释。

## 写完之后的检查清单

```
[ ] 目录名 == frontmatter 的 name
[ ] description 里有具体的用户措辞，不只有抽象定义
[ ] description 里有"即使没说 X 也该用"的兜底句
[ ] 项目里没有别的 skill 抢同一批触发词
[ ] 正文没有出现"什么时候用这个 skill"（那属于 description）
[ ] 正文 < 500 行
[ ] 每个阶段末尾都有独立一行的"停下等确认"
[ ] 正文里的相对路径和实际文件名对得上
[ ] 模板里的占位符是空的，没有残留示例值
[ ] 用两三条不含关键词的真实请求测过触发
```

最后一条最容易跳过但最重要。
