# 规格驱动开发工作流

把模糊的想法变成可执行的代码，中间经过三道文档门禁。

核心原则：**每个阶段结束都停下等确认，不要自动往下跑。** 门禁的全部价值在于
需求写错时改一段文字只要几分钟，代码写错时改一片文件要半天。一口气跑完四个
阶段，等于换个姿势 vibe coding，文档白写。

## 目录约定

每个功能一个目录，功能名用 kebab-case：

```
specs/<功能名>/
├── spec.md        阶段 1 产出
├── plan.md        阶段 2 产出
├── task.md        阶段 3 产出
└── checklist.md   阶段 3 产出（编码前必须写完）
```

## 阶段总览

| 阶段 | 产出 | 模板 | 门禁 |
|---|---|---|---|
| 1 需求 | spec.md | `templates/spec.md` | 确认范围边界与待定项 |
| 2 设计 | plan.md | `templates/plan.md` | 确认技术方案 |
| 3 任务 | task.md + checklist.md | `templates/task.md`、`templates/checklist.md` | 确认任务粒度与验收定义 |
| 4 实现 | 代码 | — | 每个任务单独确认 |

## 阶段 1：需求

读 `templates/spec.md`，按它的结构产出 `specs/<功能名>/spec.md`。

写作顺序：先写验收标准，再写功能需求。反过来写会得到一堆无法验证的愿望。

两条硬约束：

- **语言无关**。不出现方法名、类名、字段名、文件路径。自检标准：同一份 spec
  能同时指导 Go / Java / TypeScript 三种实现。做不到就是写过界了，那些内容
  属于阶段 2。
- **歧义必须暴露**。凡是想写"约定的""合理的""适当的"，说明 `假设与待定`
  一节该有一条。不要自己默选一个方案然后闷头往下走——未定的决策会以模糊措辞
  潜伏进需求条目，然后被悄悄推给下游。

`不做的事` 一节比功能需求还长是健康的。它是防止过度实现的第一道闸。

**写完停下，让用户审查 spec.md，特别是待定项。**

## 阶段 2：设计

前提：用户已确认 spec.md。

先读现有代码，理解当前架构和约定，再读 `templates/plan.md` 产出 plan.md。

「不改动」那一行是整份文档 ROI 最高的一行。不写它，会顺手"改进"相邻模块，
造成大量与需求无关的 diff。

第一期写全量架构；第二期之后只写增量。写全量架构会导致重新设计已经存在的东西。

设计要覆盖 spec 的每一条功能需求。某条需求在设计里找不到落点，说明设计不完整，
在文档里标出缺口，不要用代码硬绕。

不引入项目里没有的新依赖，除非说明理由并等确认。

**写完停下，让用户审查 plan.md。**

## 阶段 3：任务与验收定义

前提：用户已确认 plan.md。

产出两份文档，都要在编码前写完。

### task.md

读 `templates/task.md`。每个任务三件套缺一不可：

- **锚点** — 具体文件路径 + 函数名。缺了会自己找地方改。
- **验证** — 可粘贴的命令 + 预期输出。缺了"应该没问题"会被当成结论。
- **禁止** — 具体文件名或函数名。缺了会顺手重构邻近模块。

第一个任务做纯机械、不改行为的变更（改签名、加字段），先拿到一次干净的绿色
验证作为基线。粒度 2-5 分钟，超过就拆。

预期会失败的地方必须写明，例如"旧的 X / Y 两个用例会失败，这是预期的，本任务
只报告失败清单，不要改测试"。不写这句，测试会被顺手改绿，你就永久失去了
"行为确实变了"的信号。

### checklist.md

读 `templates/checklist.md`。

这不是事后验收表，是编码前把"做对了"的定义钉死。缺了它就是没靶子开枪，最后
只能靠"看起来差不多"收工。

两条写法要求：每项可观测（做 X → 看到 Y），且与实现解耦（重命名文件或移动
函数后不该失败；会失败的那条在测实现，重写它）。

**写完停下，让用户审查 task.md 和 checklist.md。**

## 阶段 4：实现

前提：用户已确认 task.md。

一次只做一个任务：

1. 说明当前在做哪个任务
2. 只写这个任务需要的代码，遵循项目 CLAUDE.md 的约定
3. 跑该任务的验证命令
4. 贴出真实输出，不是预期输出
5. 更新 task.md 的 checkbox
6. **停下，等确认再做下一个**

全部任务完成后，对照 checklist.md 逐条验证，填写验收报告：先跑命令，看输出，
再下结论。未通过和未验证的项都要如实列出。

## 关键规则

- 用户说"直接写代码"时，提醒至少需要 spec.md 才能开始。
- 需求变更先改 spec.md，再向下同步 plan 和 task。代码和 spec 漂移之后，
  spec 会变成误导性文档，比没有更糟。
- 实现阶段发现设计不对，停下来说明问题，回阶段 2 改设计，不要在代码里硬绕。
- `specs/` 目录进 git。它是 code review 的输入，reviewer 先读 spec 再看 diff。

## 端到端验收

按项目 CLAUDE.md 的要求，用 tmux 做端到端测试：启动程序，输入能触发该功能的
真实请求，观察行为是否符合验收标准，逐条对照 checklist 打勾。
